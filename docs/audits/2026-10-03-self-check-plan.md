## 已确认的问题

### 1. 多次习惯频率与打卡数据模型不匹配（P2）

**复现：** 在习惯页创建 `UI audit habit water`，频率设为每天 2 次。卡片显示 `0/2`；打卡后显示 `1/2`；再次点击变为 `0/2`；再点击仍为 `1/2`。可见入口只有“标记为完成”和“标记为未完成”，无法记录第二次完成。

**实际数据：** `frequency_count=2`、`frequency_period=day`，当天只有一条 `value=1` 的 Entry。页面不是遗漏了第二条记录，而是根本没有记录第二次完成的入口和语义。

**原因与范围：**

- `src/components/habits/shared/HabitFrequencyField.tsx:19` 对日、周频率统一允许 1–30。
- `src/components/habits/HabitCard.tsx` 的打卡处理只写入 `0` 或 `1`。
- `src/lib/utils/habit-frequency-progress.ts:73` 累加的是达标日期数，每个日期最多贡献 1。
- `src/lib/db/migrations/002_habits_focus_calendar.sql` 对 `(habit_id, date)` 建立唯一约束；现有 Boolean Habit 定义同样是一天完成或未完成。

每天 2 次的目标最高只能显示 50%。同一模型下，超过 7 次/周的目标也无法达成；后者是代码和数据约束推导出的范围，没有另行完成一周的界面复现。

**推荐修改计划：**

1. 先让现有 Boolean Habit 的配置与“达标天数”模型一致：每天固定 1，每周最高 7；编辑和 API 同时校验，避免只限制前端控件。
2. 已有或导入的超范围记录保留原值并显示解释，要求用户显式调整；不要静默改目标、历史 Entry 或统计。
3. 若保留真正的“每天 N 次”功能，单独引入计次语义：一天的 Entry 保存次数，打卡提供增加与撤销；同步修改卡片、紧凑视图、热力图、频率进度、Score、Streak、Workspace、导入和备份兼容。现有 Boolean 与 Measurable 的值不能未经迁移就重新解释成次数。
4. 更新 `CONTEXT.md`，明确“完成天数”和“重复次数”的区别。计次扩展需要独立 ADR 与迁移方案，不宜只改进度分子。

**验收：** 当前 Boolean 模型不能新建不可达成的目标；非法 API 输入不落库；旧记录不会自动变形。若实施计次扩展，则实际操作须能达到 `0/2 → 1/2 → 2/2`，刷新后仍为 `2/2`，撤销、统计和备份往返保持一致。

### 2. 习惯开始日期把 UTC 日期当作本地日期（P2）

**复现：** 上海时区 10 月 3 日凌晨创建习惯，未调整开始日期；重开编辑窗口显示 `10月2日 08:00`。日期选择器把 10 月 2 日作为已选日期，而 10 月 3 日标为今天。测试数据库实际保存 `start_date=2026-10-02`，当天打卡记录的日期却是 `2026-10-03`。

**原因与范围：**

- `src/lib/db/repositories/habit-repository.ts:188` 默认开始日期取 `now.split("T")[0]`，其中 `now` 为 UTC ISO 时间；上海凌晨 0–8 点的 UTC 日期属于前一天。
- `src/components/habits/HabitSheet.tsx:252`、`:291` 把用户选择的本地时间转成 ISO 再截取日期，本地午夜同样会退到前一天。
- 同组件 `:249`、`:288` 用 `new Date("YYYY-MM-DD")` 读取纯日期，按 UTC 午夜解释后在上海显示为 08:00。
- 提交路径 `:149` 也存在 ISO 截取，需要一起统一。

开始日期影响习惯历史和统计范围。此处已经确认默认值和编辑界面的错日；没有把所有 UTC 时间戳处理都认定为错误，也没有据此声称全部统计均受影响。

**修改计划：**

1. 把 Habit `start_date` 明确为本地日历日期，统一使用 `YYYY-MM-DD` 的解析和格式化助手，禁止经 UTC ISO 中转。
2. 在界面中按本地年月日解析纯日期；开始日期控件关闭时分选择，因为数据库并不保存时分。
3. 新建时由客户端明确提交当地的今天；后端缺省值必须有一致的时区定义，不能继续直接截取 UTC 日期。
4. 校验真实日历日期。已有开始日期不能统一加一天：无法仅凭现值判断哪些记录本来就是前一天，应保留并允许用户明确修正。
5. 排查 Habit 仓库内其他 ISO 截取日键的路径，以独立用例确认影响后再改，保留事件和专注日志的 UTC 时间戳语义。

**验收：** 在 Asia/Shanghai、UTC、America/Los_Angeles 中验证默认今天、午夜选择、保存重开和刷新；包含本地 00:30、07:59、08:01 及跨月/跨年。选择某个日历日期后，界面和 SQLite 必须保持同一日期。

### 3. ZIP 备份选择文件后未经确认就替换当前数据（P1）

**代码证据：** `src/components/settings/BackupSyncSettings.tsx:395` 的文件选择回调直接调用 `importData(file)`；`src/lib/hooks/useAccountData.ts:35` 解析后立即调用恢复；`src/lib/backup/local-backup.ts:53` 默认 `replace=true`。本地 ZIP 路径没有使用 WebDAV 和 `.db` 恢复已有的确认弹窗。

Computer Use 已确认导出入口成功；IAB 的文件选择没有出现可操作的原生选择器，因此实际导入交由补充的 Playwright 界面脚本验证，不能将代码推断写成 Computer Use 已复现。

**实际复现：** 创建任务 A，使用设置页导出 ZIP，再创建任务 B，然后用同一设置页的文件输入选中刚导出的 ZIP。没有点击任何恢复确认按钮，应用立即发送替换请求；响应为 200，`replace=true`，可见确认弹窗数量为 0。A 保留、B 消失；重新进入任务页仍是这个结果。此场景执行一次，同时以请求、数据库读取和界面断言确认。

预期是解析和预览之后明确确认替换，实际是选文件就恢复。证据为 `evidence/zip-import-probe.cjs`、`zip-import-result.json`、`zip-import-before.png` 和 `zip-import-after.png`。脚本执行命令：

```bash
node .scratch/audits/2026-10-03-ui-check/evidence/zip-import-probe.cjs
```

关键结果：`confirmed=true`、`confirmationClicks=0`、`beforeTaskSurvives=true`、`afterTaskSurvives=false`。该脚本仅应针对隔离测试库运行。

**修改计划：**

1. 把“解析备份”和“执行恢复”分开。选文件只解析与预览，展示备份时间、内容数量和替换范围。
2. 显式说明当前数据将被替换，确认后才调用恢复；取消时不发送恢复请求。
3. 使用现有恢复确认组件，并保留当前自动快照与事务保护。快照可恢复性减轻损失，但不能替代用户对替换动作的知情确认。
4. 增加端到端用例：选文件不会写库，取消保留 B，确认后才移除 B；损坏 ZIP 不触发恢复。

## 可独立安排的优化

### 已完成日志的空态与实际范围不一致（P3）

Computer Use 勾选今日任务后，日志显示“暂无已完成任务”；数据库的完成状态和时间均正常。`CompletedTasksSheet.tsx:144` 显式排除今天，而主列表刻意保留今天完成的任务。这属于既有的分区行为，不是完成操作失效。

但空态写“完成的任务会显示在这里。去任务列表勾选条目吧！”会让用户按提示操作后仍看到空白。推荐保留当前分区策略，明确日志仅收录昨天及以前，并提示今日完成项仍在任务列表。跨午夜是否自动重新归档需要另做时间推进测试，本轮没有确认该行为。

### 语言与架构说明需要同步（P3）

`AccountSection.tsx:21`、`:24`、`:33`、`:40` 的本地模式文案为硬编码中文，没有进入翻译字典。英文浏览器会话也显示中文，已用界面断言与截图确认。建议归入现有中英字典，并把用户无需理解的库名移入技术详情。

根目录 `AGENTS.md` 和 `CONTEXT.md` 部分账户、云端、同步说明仍描述旧 Supabase 模式；`AGENTS.md` 引用的 `.claude/skills/verify/SKILL.md` 已不存在。当前 `AuthProvider` 提供本地身份，ADR 0023 明确本地 SQLite。建议以当前实现和 ADR 为依据更新说明，将历史设计明确标为历史，补上有效的验证入口；不因旧文档而恢复已撤下的功能。

## 修改顺序与完成标准

| 顺序 | 工作                     | 完成标准                                               |
| ---- | ------------------------ | ------------------------------------------------------ |
| 1    | 补齐 ZIP 替换恢复确认    | 选文件不写库，确认前后有真实数据库断言，自动快照保留   |

每个功能修复先补能捕获上述具体现象的回归，再验证对应实际界面流程。最后运行 `CI=true npm run validate` 和相关桌面/移动端到端检查。只有修改 Service Worker 时才要求额外生产构建及离线验证；不能用开发模式通过来宣称离线已验证。
